P0 · 6.1 递归函数跨 case 撞名致伪 SAT

根因
z3-solver 5.0 起，同名的 z3.RecAddDefinition 第二次会抛 "recursive function ... already defined"。 而早期三个方法用 per-builder slice_id 命名递归函数： _sum_z3_sequence → __sum_seq_{id}、_prod_z3_sequence → __prod_seq_{id}、_sum_tensor_elements → __sum_tensor_{name}_{id}。 _slice_counter 在每个新 Z3ConstraintBuilder 实例里 从 0 重置，全模块又共用 z3.main_ctx()（全局上下文）。
→ case 1 注册 __prod_seq_1；case 2 计数器又从 1 起，再注册 __prod_seq_1 → 抛错 → 被 add_constraint 的 except Exception 吞掉（仅 logger.error）→ 该约束没进 solver → solver 在“部分约束”上 check() 返回 sat → 生成违反被丢约束的用例 → 伪 SAT。

示例 A · z3 5.0.0 实证复现（修复前的 bug 机制）

# 全局 ctx，第二次同名 RecAddDefinition 必抛——这正是跨 case 撞名的根
P1 = reg_prod('__prod_seq_int', int_seq_sort)   # case 1: OK
P2 = reg_prod('__prod_seq_int', int_seq_sort)   # case 2: 同名再注册
→ Z3Exception: recursive function __prod_seq_int already defined
# str(SeqSort) 各异：'Seq(Int)' / 'Seq(Real)'，SeqSort 无 .domain()

示例 B · 修复前后的生成日志对比（ConfusionTranspose，含 prod 约束）

# 修复前（伪 SAT）：prod 约束被丢，sat on 部分约束，99/100 用例违反 prod
[FAIL] prod(shape.range_value) == prod(x.shape): recursive function ... already defined
Solve result: sat                          # ← sat 但约束被丢，伪 SAT

# 修复后（6.1）：prod 约束保留，solver 在完整约束上 sat，0 [FAIL] / 0 [PSEUDO_SAT_RISK]
grep -cE '\[FAIL\]|\[PSEUDO_SAT_RISK\]' generation.log   → 0
grep -cE 'Solve result: sat'            generation.log   → 20   # 全部 sat，约束未被丢

修复：与既有 _PROD_SHAPE_REC_FUNCS 同构的幂等注册

# 模块级注册表（跨 builder 共享 z3.main_ctx()，与 param_var_definition 同模式）
_PROD_SEQ_REC_FUNCS = {}      # key: name(str) -> FuncDeclRef

    ProdSeq = z3.RecFunction(name, seq_sort, z3.IntSort())
    ...
    z3.RecAddDefinition(ProdSeq, ...)         # 仅首次注册
    _PROD_SEQ_REC_FUNCS[name] = ProdSeq
    return ProdSeq(seq)

# 三方法改为一行委托（保留 rank==1 副作用与返回表达式）
def _prod_z3_sequence(self, seq): return _get_or_register_prod_seq(seq)
def _sum_z3_sequence(self, seq, element_sort=None): return _get_or_register_sum_seq(seq, element_sort)
def _sum_tensor_elements(self, tensor_var):
    SumArr = _get_or_register_sum_tensor(tensor_var.get_element_sort())
    ...                                       # self.builder.solver.add(rank==1) 副作用保留
    return SumArr(arr, z3.IntVal(0), n_elements)
为何 ten.html 原方案不够
① 只点名 _prod_z3_sequence/_sum_z3_sequence，漏 _sum_tensor_elements（同一 bug 模式：slice_id 命名 + RecAddDefinition）。
② 片段硬编码 "__prod_seq_global"，注册表键用 (str(seq_sort),)——若同进程出现不同 seq_sort，键不同不早返回，却同名注册仍抛。本实现改为函数名从 str(sort) 派生（_sanitize_sort_name），保证同 sort 同名复用、不同 sort 不同名不撞名。
③ get_next_slice_id/_slice_counter 保留——其它路径（__in_/__notin_/max-min 命名）仍用，只是不再用于 RecFunction 命名。

P0 · 6.2 add_constraint 失败不可观测

根因
add_constraint 的 except Exception as e: logger.error(...) 只记日志，丢弃的约束无任何标志位；solve() 仍以“部分约束”返回 sat 并落盘。这是 6.1 伪 SAT 能静默发生的制度性前提——丢了约束谁都不知道。
修复
__init__ 增 _dropped_exprs=[] / _sat_with_drops=False；except 追加 self._dropped_exprs.append((expr_name, expr_str, str(e)))；solve 在 sat 且有丢弃时置 _sat_with_drops=True 并 logger.warning("[PSEUDO_SAT_RISK] ...")。仅可观测，不阻断、不判 unknown——阻断统一交给 P1 的 post_check，避免强制 unknown 回归当前通过算子。

示例 · 6.2 端到端实证（违禁 expr 触发 except → tainted 告警）

b = Z3ConstraintBuilder()
b.add_constraint("c_bad", "sum(x for x in [1,2]) == 1")   # converter 抛 NotImplementedError（generator 未支持）
b.solve()
[FAIL] sum(x for x in [1,2]) == 1: sum() with generator expression is not yet supported
[PSEUDO_SAT_RISK] sat with 1 dropped expr(s); defer to post_check: [('c_bad', ...)]
# _dropped_exprs 非空、_sat_with_drops=True；产出仍保留（不阻断），交给 post_check 兜

P1 · 6.3a/6.3b post_check 安全网——理论不完备的兜底

根因
6.1/6.2 堵住“约束被丢”的伪 SAT，但 Z3 还有另一类问题：约束被加进 solver，但编码 unsound——solver 找到的 model 在 realized（落地的）用例上实际违反 expr。典型如 len(out.shape) >= len(x.shape)：在 Z3 Seq 上 solver 找的 model 看似满足，但 realized shape 列表并不满足。这类需 6.3c 编码增强根治；post_check 是兜底：生成后用 Python 直接 eval realized 用例是否真满足 expr，违例则过滤。
为何要 6.3b 保真边界
eval 有保真陷阱：range_value 在 realized case 里可能是标量/列表，与 expr 的 Z3-array 语义不对应。如 prod(shape.range_value) 期望 range_value 是序列，但 realized 里 shape.range_value = 65534（标量）→ prod(65534) 抛 TypeError。若把 eval-error 当违例过滤，会误杀通过用例（False positive）——比不兜底更糟。

修复 6.3b · eval-error ≠ 违例

def eval_expr(expr, namespace) -> (ok, err):
    try: return bool(eval(expr, {'__builtins__': SAFE_BUILTINS}, namespace)), None
    except Exception as exc: return False, f"{type(exc).__name__}: {exc}"

# 仅 err is None 且 ok=False 才算真违例（计入 violated_count、可过滤）
if err is not None:        case_eval_error = True      # eval_unreliable，绝不过滤
elif not ok:           case_clean_violation = True  # 真违例，过滤
# 既无 clean-False 又无 eval-error → fully-verified pass
# 补 prod（math.prod）/ __len__ 扩展可 eval 范围
SAFE_BUILTINS["prod"] = _prod
def __len__(self): return len(self.range_value)   # len(param)→len(range_value)；标量则抛→eval_error（诚实）

P1 · 6.5 #8 算子专属提取模块——文档自相矛盾的源头纠错

根因
aclnnFusedLinearCrossEntropyLossGrad 文档参数表↔公式自相矛盾：
  • 公式（49 行）：grad_weight = softmax^T · input ∈ R^{V×H} → weightGradOut 第 2 维 = H = input.shape[1]。
  • 参数表（261 行）：“weightGradOut 第 2 维长度与输入 grad 长度相同” → = BT = grad.shape[0]。
constraint-extractor 忠实提取参数表文本 → 落 weightGradOut.shape[1] == grad.shape[0]（绑 BT）→ NPU 运行时 Expected [V, H]，BT≠H 时报 EZ1001 161002: Expected [128,128] but got [128,8]（BT=8, H=128）。
修复
用 scripts/select_prompt.py 的 operator_name_eq 机制（nz_matmul.md 先例），在 init_run 阶段把算子专属模块装配进 inputs/prompt_v1.md（extractor 读取之前），据此落 weightGradOut.shape[1] == input.shape[1]（绑 H，允许 BT≠H）+ maskedTarget/targetMask 值域。仅该算子命中，不污染其他算子。
为何优于 6.4 supplement
6.5 主（持久/版本化、前置生效、自动命中、修法正确绑 H）；6.4 per-run supplement 降为兜底（且补丁内容纠正为 replace_constraint 绑 input.shape[1]，非 BT==H 退化 band-aid）。

共同主线与互补

  • P0 堵“约束被丢”的伪 SAT（源头）：6.1 让 prod/sum/tensor-sum 递归约束不再跨 case 撞名丢弃；6.2 让丢弃可见。实证：ConfusionTranspose 生成 0 [FAIL]/0 [PSEUDO_SAT_RISK]，prod 约束保留。
  • P1 兜“约束被加但 unsound”的伪 SAT（兜底）：6.3a/b 用 Python eval realized 用例过滤违例 + 补采 + shortfall。实证：ForeachErf 8-9 违例→过滤补采→kept=30/0 残留。
  • 互补不重叠：6.1 防约束丢失（prod/sum 类），post_check 兜约束被加但编码 unsound（len 类可 eval 的）。对不可 eval 的（如 prod 在标量 range_value 上）post_check 诚实标 eval_unreliable 不过滤——由 6.1 已在源头保证其不丢，故无须再兜。
  • P1 另一支：6.5 从源头纠正 #8 文档矛盾（绑 H），与 6.1/6.3 正交——它解决的是 extractor 的输入（prompt）问题，非 Z3 求解问题。
  • 诚实降级原则贯穿：6.2 不阻断只告警、post_check 不可 eval 不过滤、补采不足标 shortfall 如实落盘——任何时候不假装成功。
