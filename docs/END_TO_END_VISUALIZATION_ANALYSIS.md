# 算子测试系统端到端可视化分析

日期：2026-09-24。性质：基于仓库源码的分析与待讨论方案，不是已批准的实现规格。
> 注：本文写于 .claude/ → .opencode/ 迁移之前，文中 `.claude/...` 路径为当时快照，
> 现行对应位置见 `.opencode/`（agent/skills/command/plugins）。

> 后续范围修正：用户明确要求可视化与业务代码解耦，只读 run_state.json 及过程文件，不侵入修改业务。本文件第 7、8 节提出的运行控制桥接及业务修复不再是当前建议路线。以独立只读适配层为准；真实样例核查见 RUN_ARTIFACT_SAMPLE_ANALYSIS.md。

## 1. 目标与分析边界

用户目标是整个项目的端到端可视化，强调美观、直白，并用于演示和汇报。现有静态页面只是早期尝试，不作为产品边界。

建议产品定位为“算子测试工作台”：从任务输入、范围选择、自动执行、人工决策到结果解释，使用同一任务上下文。演示与汇报是同一过程的不同阅读方式，不另造一套与真实运行脱节的数据。

本次只读分析了主协调技能、批处理技能、状态推进器、人工约束接入、进度采样、调度钩子、执行适配、产物协议及知识沉淀规则。没有运行真实算子、连接执行机、调用模型或部署服务；当前工作区没有 runs 运行数据及 .venv 环境。涉及运行故障的判断均为静态路径分析，需后续集成验证。

## 2. 系统实际构成

不是一个已经拥有完整后台任务服务的网页应用。当前系统由四部分共同完成：

1. 命令行智能体会话：理解输入，委派角色，提出问题，等待结果，组织恢复。
2. 确定性业务脚本：初始化、校验、状态推进、用例生成、执行适配、版本更新。
3. 独立进程与远端执行：用例生成可脱离会话存活；实际测试通过执行适配器运行。
4. 文件产物：任务状态、约束、用例、诊断、更新记录及日志是各阶段交接依据。

可视化需要连接这四部分。只读取完成文件无法提供完整的发起、交互、停止与恢复体验。

## 3. 端到端能力地图

| 环节 | 当前能力与主要事实来源 | 用户应看到/完成的事情 |
|---|---|---|
| 新建任务 | init_run.py；文档、源码和补充证据快照；参数与知识装配冻结 | 选输入材料，知道缺什么，确认实际测试范围 |
| 批次任务 | init_batch.py、batch_state.py；算子串行认领与恢复 | 看文档清单、顺序、成功/失败/待处理，而非默认并发 |
| 场景选择 | scene_scan.json、selection.json、scene_directive.md | 按设备→模板→特性参数逐级选择；解释固定或展开的影响 |
| 场景冲突 | scene_conflicts.json | 展示双方取值、冲突原因，允许返回修改或明确继续 |
| 首轮提取 | 文档提取与可选源码分析并行，随后汇合 | 看两条证据来源及各自产物，区分确认事实与不确定候选 |
| 补充及争议 | constraints_patch.json、conflict_candidates.json | 查看补充依据；源码与文档争议可异步裁决，不一律阻断 |
| 约束检查 | constraint_check.json；独立检查和修复角色 | 展示本轮第几次检查、待修复项、复检结果 |
| 用例生成 | generation_progress.py；进程状态、逐平台数量 | 区分智能体已交棒与生成仍运行；展示已完成数量和活动证据 |
| 执行准备与执行 | execute_cases.py、executer/；不同框架及策略 | 看实际执行平台、准备/上传/执行/收集进展，解释执行分支 |
| 质量评审 | quality_gate.json、execution_result.json | 区分产物有效性、执行成功、精度结果及非阻断告警 |
| 失败诊断 | analysis.json、source_evidence.json、设备日志 | 按失败簇说明根因、受影响用例、证据、建议动作 |
| 自动更新 | constraint_update_state.py、constraint_update.json | 展示发现→修改→预期效果；保留上一轮不可变基线 |
| 人工介入 | 检查点、constraints_copy.json、apply_human_constraints.py | 补证据、改约束、批准有限继续或停止，并看到处理回执 |
| 再次验证 | 回归检查、语义检查、生成与执行 | 展示修复是否引入回归，不把“已修改”直接当“已修复” |
| 收尾 | 终态、批次汇总、知识更新提案 | 说明结论范围、未解决项；知识沉淀单独审核 |
| 覆盖分析 | 参数组合分析器及独立源码覆盖报告 | 分开展示参数取值/组合覆盖与函数/语句/分支覆盖，注明关联范围 |

## 4. 必须保留的业务语义

- 外层测试迭代与内层约束检查是两套计数。例如“测试第 2 轮，约束第 3 次检查”，不能合并成“第 5 轮”。
- 完整提取只在首轮发生；执行反馈轮最小修改上一版约束，不重走全部提取流程。
- 仅约束提取的任务也可 SUCCESS，但没有执行用例。必须将成功范围随结果展示。
- 多平台生成不等于多平台执行；当前执行选择匹配平台，界面要分别列出生成范围与实际执行范围。
- 普通、融合、TTK 等路径的精度验证能力和门禁语义不同，应读取实际结果及参考实现来源，不从 real 模式推断精度已验证。
- 混合根因不能自动按约束问题处理；用户批准的范围需要明确记录。
- 人工编辑提交、约束校验通过、下一轮已开始是三个不同事件。
- 冲突裁决可能异步到达；已通过检查的约束发生变化后必须重新检查。
- 停止命令行会话不等于停止脱离会话的生成进程，也不证明远端执行停止。
- 知识更新是独立的、有验证证据及人工批准的收尾动作，不是测试成功后自动改全局知识。

## 5. 已确认的集成缺口

### 5.1 会话、业务与进程没有统一关联

`.claude/hooks/trace_hook.py` 记录 session_id、agent_id、agent_type 和开始/结束，没有明确的 run_id、iteration、stage_instance_id、产物版本或成功结论。不能仅按时间接近就认定某智能体属于某一轮任务。

建议补充任务/轮次/阶段实例关联，区分角色开始、角色返回、产物校验通过、业务阶段完成。角色结束本身不是业务成功。

### 5.2 人工等待路径与统一状态模型不一致

主协调技能规定 AWAITING_HUMAN_CONSTRAINTS，但 scripts/run_state.py 的 ALLOWED_STATES 未包含它，flow_control.py 也没有对应推进规则。人工接入脚本使用自己的原子写入逻辑。

人工接入的 `_apply` 创建约束与备份并进入 UPDATE_CONSTRAINTS，没有在该路径创建 constraint_update.json；统一推进器的 decide_UPDATE_CONSTRAINTS 又要求这份报告。按这些代码直接衔接存在停留风险，需集成测试确认并统一人工/自动更新契约。

### 5.3 批次终态口径存在差异

主协调技能要求用户停止后完成批次项，但 batch_state.py 的终态集合与命令行参数选项不包含 STOPPED_BY_USER。前端接入批次停止前需明确“取消当前算子”“停止整个批次”的不同语义并修复口径。

### 5.4 长任务控制尚不是统一服务

生成器已有启动、采样和等待入口；人工文件监听依赖会话恢复重新挂起。未发现可直接供浏览器使用的完整运行会话管理及用户问题回传协议。不能将“恢复”做成无条件重跑：生成脚本重跑可能覆盖已完成平台产物。

### 5.5 覆盖率不是当前主链路统一生成的最终结论

参数组合覆盖分析器以约束和用例为输入；源码覆盖报告位于独立目录。当前主协调路径未显示统一的自动覆盖采集和任务版本关联步骤。方案需要把报告生成/导入与任务、平台、源码版本、用例集合绑定；无法关联时显示独立报告，不自动归到最近一次测试。

### 5.6 文档不是唯一真实依据

不同技能对参考结果生成与默认执行行为存在表述差异。设计需建立能力清单，以入口参数、执行实现、产物与集成测试共同核实，不把文档中的能力直接做成可用按钮。

## 6. 建议的产品组织

### 6.1 任务入口

单算子/批次入口；输入文档、可选源码与补充证据；展示环境就绪情况、框架适配范围、测试模式及预算。高级参数折叠。任务初始化后的场景识别与用户选择应显示为正常流程，不伪装成创建失败。

### 6.2 任务工作台：核心页面

顶部固定任务、范围、实际状态和当前行动。左侧为有层次的过程导航，中间是当前阶段的内容，右侧按需打开证据详情。底部或独立抽屉提供运行记录，默认不铺满终端日志。

主流程按准备、提取、检查、生成、执行、评审与迭代组织；点击阶段展开智能体、子步骤、检查次数、产物与证据。不同框架显示真实适用步骤；仅约束任务明确跳过执行。

当前阶段示例：生成时展示各平台已生成数量及进程活动；诊断时展示失败簇与归因证据；更新时展示约束前后变化和回归检查；等待时展示具体决策卡。

### 6.3 人工决策

统一的待办卡包含：触发原因、受影响范围、证据、可选动作、动作后果、所对应的任务轮次与版本。区分阻断型待办和非阻断争议。过期决定不得作用于已推进的版本；重复提交必须可安全识别。

### 6.4 演示与汇报

在同一任务里提供“实时过程”和“历史回放”。回放使用已经记录的事实，明确标识时间和回放模式；历史中缺失的细节显示未知，不补造智能体活动或进度。

汇报视图保留范围、过程关键节点、结果、迭代差异、覆盖缺口和未决问题。可以下钻到证据，避免汇报结论与操作页数据口径分离。

### 6.5 批次与成果

批次页面按现有串行策略展示队列、当前任务及每个算子结果。成果视图按任务关联产物，不要求用户理解目录结构。知识提案作为可选收尾入口。

## 7. 技术方向与取舍

方案 A：只读过程观察和回放。能够先验证信息呈现，但无法完成页面内的任务发起与人工闭环，只适合明确标注的阶段成果。

方案 B：保留现有智能体编排与确定性脚本，增加本地运行桥接、统一事件与交互服务。建议作为目标路线：业务资产可复用，同时补齐完整交互。前提是先验证实际运行环境中的会话事件与问答接入，当前尚未验证。

方案 C：将整个智能体编排迁入自建后台运行引擎。控制边界更完整，但会改变项目的命令行原生设计，带来角色隔离、恢复和工具权限等大范围重建，不作为本轮默认方案。

方案 B 的建议关系：浏览器工作台→本地任务与交互服务→运行环境适配器→现有智能体及脚本。事件与产物由本地服务关联后供界面展示；状态仍由现有规则和统一后的写入入口裁决，前端不直接修改状态文件。

新增服务应管理会话生命周期、问题/答复、进程归属、恢复与控制回执；业务脚本继续保持确定性。该服务改变了系统边界，需要正式设计，不能悄悄把模型调用塞回业务脚本。

任务、轮次、阶段实例、角色实例、产物版本、决策请求、执行尝试是建议的关键对象。事件至少关联这些对象中的适用标识，并带唯一编号和时间，便于断线重连及回放。事件用于观察，经过校验的状态和产物仍是业务依据。

网页与服务仅在本机运行；若启动服务默认监听 0.0.0.0。新增写入控制需要同源限制、访问校验和受限动作入口，不能暴露任意命令执行。访问已有执行机属于测试能力接入，当前分析没有执行任何远端操作，也不授权新增云资源。

## 8. 推进顺序与验收

第一步，核实控制链路：选定运行环境，用一个任务验证启动、收到问题、提交答复、状态推进、断开恢复；先解决人工状态与批次终态契约差异。

第二步，设计覆盖完整链路的视觉方案，而不是先细化局部约束表格。展示准备、运行、等待、失败、修复、结束六类关键画面。

第三步，完成一个端到端实现切片：页面创建任务→选择场景→提取检查→生成→执行→诊断→人工或自动修复→再次验证→结果。每个环节都接真实状态；可用隔离样例验证界面，但必须清楚标识模拟数据。

第四步，在这条切片上扩展框架分支、批次、覆盖报告关联、历史回放与知识提案。

验收重点：

- 用户能在同一任务中理解当前阶段、输入输出及下一步，而不依赖终端解释。
- 约束检查循环与测试迭代分别呈现。
- 智能体返回后仍能正确显示后台生成活动。
- 待办提交有接受、校验、消费和继续的清晰回执。
- 页面刷新不会重复启动任务；恢复不覆盖已完成平台用例。
- 终止会话、停止进程及停止远端执行的回执分开，未知状态不报已停止。
- 约束提取成功、执行成功、精度验证与不同覆盖率口径互不混淆。
- 实时与回放使用同一事实模型；任何缺失证据明确显示。
