3. 根因：确定性 Z3 生成器产生“伪 SAT”

3.1 机制：约束被静默丢弃

用例生成器（agent/generators/param_constraint_solve/）把约束 expr 逐条转成 Z3 表达式后喂给 solver。问题出在 z3_expression_solver_utils.py 的 add_constraint：

# agent/generators/param_constraint_solve/z3_expression_solver_utils.py:185-198
def add_constraint(self, expr_name, expr_str, is_print_log=False):
    try:
        tree = ast.parse(expr_str, mode='eval')
        converter = ASTtoZ3Converter(self)
        z3_constraint = converter.visit(tree.body)   # ← prod/sum 在此抛 "recursive function __prod_seq_1 already defined"
        if z3_constraint is not None:
            self.solver.assert_and_track(z3_constraint, expr_name)
    except Exception as e:
        logger.error(f"[FAIL] {expr_str}: {e}")  # ← 第198行：捕获后仅记日志，约束被静默丢弃
致命链路
converter.visit() 在转换 prod(...) / sum(...) 时调用 _prod_z3_sequence / _sum_z3_sequence， 后者用 z3.RecAddDefinition 注册名为 __prod_seq_<slice_id> 的递归函数。 z3-solver 5.0+ 对同名递归函数第二次注册会直接抛异常。异常被第 197 行的 except Exception 吞掉——该约束从未进入 solver。solver 只对剩余的静态约束求解，返回 sat， 落盘用例便违反了被丢弃的 prod/sum 约束，即“伪 SAT”。

3.2 递归函数重名的根因（已有修法但未覆盖全路径）

仓库已为 shape 维度乘积这条路径做了幂等注册修复，见 param_var_definition.py:22-48：

# 已修复的路径（shape 总元素数乘积）——按名幂等注册，已注册则复用
_PROD_SHAPE_REC_FUNCS = {}
def _get_or_register_prod_shape(prod_func_name, seq_int_sort):
    existing = _PROD_SHAPE_REC_FUNCS.get(prod_func_name)
    if existing is not None: return existing   # 幂等复用，避免重定义异常
    prod = z3.RecFunction(prod_func_name, ...)
    z3.RecAddDefinition(prod, [s_var], ...)
    _PROD_SHAPE_REC_FUNCS[prod_func_name] = prod
    return prod
# 但 expr 求解路径用的是另一套——未做幂等，靠 per-builder slice_id 去重
# expression_preprocess_utils.py:747-786
def _sum_z3_sequence(self, seq, element_sort=None):
    slice_id = self.builder.get_next_slice_id()        # ← 每个 builder 实例计数器从 1 重置
    func_name = f"__sum_seq_{slice_id}"          # ← 跨 builder / 跨 case 同名
    SumSeq = z3.RecFunction(func_name, seq_sort, element_sort)
    z3.RecAddDefinition(SumSeq, [seq_var], ...)        # ← 第二个 case 即抛 already defined
    return SumSeq(seq)
def _prod_z3_sequence(self, seq): ... # 同结构，func_name=__prod_seq_{slice_id}
为什么复发
整个模块共用 z3.main_ctx()，递归函数名是 全局可见 的。而 get_next_slice_id() 是 每个 Z3ConstraintBuilder 实例的局部计数器——每跑一个 case / 每个平台都新建 builder，slice_id 从 1 重来，于是第二个 builder 注册 __prod_seq_1 时与第一个撞名抛异常。shape-product 路径用全局字典按名幂等注册绕开了此问题；_prod_z3_sequence / _sum_z3_sequence 这条 expr 求解路径却没套用同一修法——这是缺陷的核心。

6. 修复方案

6.1 P0 — 修递归函数重定义（直接干掉 #4/#9，缓解 #2）

方案 A：把幂等注册套用到 expr 求解路径（推荐，最小改动）

把 param_var_definition.py 已验证的 _get_or_register_prod_shape 模式复制到 expression_preprocess_utils.py 的 _prod_z3_sequence / _sum_z3_sequence：

# 新增模块级注册表（与 _PROD_SHAPE_REC_FUNCS 同构）
_PROD_SEQ_REC_FUNCS = {}
_SUM_SEQ_REC_FUNCS  = {}

def _prod_z3_sequence(self, seq):
    seq_sort = seq.sort()
    # 用 seq_sort 的 sort() 作为幂等键，不再依赖 per-builder slice_id
    key = (str(seq_sort),)
    existing = _PROD_SEQ_REC_FUNCS.get(key)
    if existing is not None:
        return existing(seq)            # 复用已注册函数，不再 RecAddDefinition
    ProdSeq = z3.RecFunction("__prod_seq_global", seq_sort, z3.IntSort())
    seq_var = z3.Const("__prod_seq_global_arg", seq_sort)
    z3.RecAddDefinition(ProdSeq, [seq_var],
        z3.If(z3.Length(seq_var) == 0, z3.IntVal(1),
              seq_var[0] * ProdSeq(z3.SubSeq(seq_var, 1, z3.Length(seq_var) - 1))))
    _PROD_SEQ_REC_FUNCS[key] = ProdSeq
    return ProdSeq(seq)
# _sum_z3_sequence 同构改造（注意 element_sort 分 Int/Real 两键）

预期：消除 already defined 异常，prod/sum 约束真正进入 solver → ConfusionTranspose、GroupedMatMulAlltoAllv 从伪 SAT 转为真 SAT（或诚实的 unsat）。这条已在本仓库 shape-product 路径验证可行，风险低。

6.2 P0 — 让 add_constraint 不再静默丢约束（防御纵深，兜底所有 expr 转换失败）

方案 B：失败必须可观测、可阻断

def add_constraint(self, expr_name, expr_str, ...):
    try:
        ...
        self.solver.assert_and_track(z3_constraint, expr_name)
    except Exception as e:
        logger.error(f"[FAIL] {expr_str}: {e}")
        self._dropped_exprs.append((expr_name, expr_str, str(e)))  # 记录被丢约束
        # 关键：solve() 后若有 dropped_exprs 且 check==sat，
        # 必须 post_check 复算或直接判 unknown，禁止当作干净 sat 落盘用例。

根因：当前 except 吞掉异常后 solver 仍以“部分约束”返回 sat 并落盘，这是伪 SAT 的制度性入口。修法是让“有约束被丢”的 sat 不能直接当成功——要么走 post_check 复算全部 expr（已有 post_check_cases.py），要么直接判 unknown 退回 0 用例。两害相权取 post_check 过滤+补采，既保留产出又保证正确性。

6.3 P1 — 修 Z3 理论不完备（#5/#6/#7、#10、#2）

方案 C：把 post_check 纳入生成主流程 + 针对性增强编码

  • len(shape) 不完备（Foreach 三连）：把序列长度提升为显式 Int 标量 L_out / L_x，约束 z3.Length(seq)==L_* 并对 L_out >= L_x 求解，避免直接对 Length 推理。
  • floor 除法 + 负索引（Im2col）：负索引 shape[-1] 改写为 shape[len-1] 正索引并约束 len>0；floor 除法项先对自变量定上下界再做整数除法建模，或对 Im2col 这类公式驱动算子改走 构造式（给定 self/pad/dil/k/stride，直接算 out.shape，不走 Z3 反解）。
  • 广播 unknown（BlendImagesCustom）：广播依赖改构造式（定主形状→派生从属），或 unknown 显式降级枚举兜底。
  • 统一兜底：把 scripts/post_check_cases.py 去掉硬编码 run 路径、参数化后接入 generate_cases.py，生成后立即对全部 constraints_in_parameters[].expr 复算，违反项过滤并补采至 case_count——这一步能拦住所有“Z3 说 sat 但其实违反”的逃逸，是上述增强失效时的最终安全网。

方案 E：把 #8 的纠错约束从单 run 的 supplementary-doc.md 提升为 prompts/modules/ 下按算子名命名的稳定模块

核实：inputs/supplementary-doc.md 确为单 run、单算子产物——落在 runs/<run-id>/inputs/，由 source-analyst（--src 时）或 diagnose（iter_N/supplement_additions.md，origin=diagnose_inferred）产出，跨 run 不留存、每次需重提；与全局基础提示词 operator_constraints_extract_v4.md 是两类东西。用户提议把它沉淀为 prompts/modules/ 下、按算子名命名的稳定模块——本仓库已有该机制，可直接落地：

  • scripts/select_prompt.py 在 init_run 阶段按算子特征装配 base prompt + 命中模块 → inputs/prompt_v1.md，在 extractor 读取之前完成（init_run.py:395 assemble(...)）。
  • 其 trigger_matches 已支持 operator_name_eq（精确算子名）触发，仅该算子命中、不污染其他算子；prompts/modules/nz_matmul.md 已用 operator_name_eq: aclnnBatchMatMulWeightNz 作为单算子先例。
  • 新模块不在 MODULE_ORDER 固定序中，classify() 会把它排到尾部加载，行为正确。

因此新建模块文件（不叫 supplementary-doc.md，按算子名命名）：

--- prompts/modules/aclnnFusedLinearCrossEntropyLossGrad.md ---
module: aclnnFusedLinearCrossEntropyLossGrad
description: 修正文档参数表↔公式冲突：weightGradOut.shape[1] 绑 H 不绑 BT；maskedTarget/targetMask 值域
triggers:
  - kind: operator_name_eq
    value: "aclnnFusedLinearCrossEntropyLossGrad"
depends_on: []
---
## 算子专属提取规则（消解文档自相矛盾，非通用模式）

1. weightGradOut.shape[1] 必须绑 input.shape[1]（=H），不得绑 grad.shape[0]（=BT）
   - 文档参数表（weightGradOut 行）写“第2维长度与输入grad长度相同”（=BT），与公式第49行
     grad_weight = softmax^T · input ∈ R^{V×H}（第2维=H）矛盾。
   - 以公式为准：NPU 运行时 Expected [V,H]；失败例 BT=8、H=128 证明 BT≠H 才是常态，
     强制 BT==H 会退化测试。落 expr：weightGradOut.shape[1] == input.shape[1]
     （等价 == weight.shape[1]，因已有 weight.shape[1]==input.shape[1]）；
     禁止 weightGradOut.shape[1] == grad.shape[0]。
2. maskedTarget ∈ [0, weight.shape[0]-1]：局部词表索引，负值越界触发 aicore 507015。
   expr：0 <= maskedTarget.range_value and maskedTarget.range_value <= weight.shape[0] - 1。
3. targetMask ∈ [0,255]：dtype=UINT8，8bit 掩码。
   expr：0 <= targetMask.range_value and targetMask.range_value <= 255。
4. 维护注记：本模块为消解文档参数表↔公式冲突的算子专属纠错；若官方文档修订使二者一致，应同步删除本模块，避免长期堆积。

7. 结论

一句话
本轮跑批 9 失败分三类：① 7 个同根因（生成器锅）——确定性 Z3 生成器在 add_constraint（z3_expression_solver_utils.py:197-198）把 prod/sum 递归函数重定义异常 静默吞掉并丢弃约束，solver 对剩余约束返回 sat，落盘用例违反被丢约束——即“伪 SAT”。_prod_z3_sequence / _sum_z3_sequence 没套用仓库已有的幂等注册修法（_get_or_register_prod_shape），是缺陷核心；另有 Z3 序列长度/floor 除法不完备（P1 靠 post_check 兜底）。② 1 个约束本身有误（#8，约束提取锅）——constraints.json 把 weightGradOut.shape[1] 错绑到 grad.shape[0]（BT）而非 weight.shape[1]（H），外加 maskedTarget/targetMask 值域空，Z3 未伪 SAT 而是照错约束解出违法用例，实跑 95/100 挂；补丁 supplement_additions.md 已就绪、未跑补充管线故打 MAX_ITERATIONS，可直接恢复。③ 1 个执行机配置缺失（#3，非代码 bug）。
最快见效
先做 6.1 + 6.2（两条 P0，改动小、已有同构先例），可直接救回 ConfusionTranspose、GroupedMatMulAlltoAllv 两个 100% 失败的算子，并堵住所有“吞异常→伪 SAT”的逃逸入口；再做 6.3 把 post_check 接入主流程作为全局安全网；#8 走 6.5 算子专属模块（绑 input.shape[1]、勿用 BT==H band-aid），配 6.3 post_check 兜底，6.4 per-run supplement 降为确定性补救。
